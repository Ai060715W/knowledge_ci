Knowledge CI

面向代码仓库的持续知识发现、证据验证、主动注入、风险治理与增量演进系统。 它不是把文档放进向量库，而是让软件知识拥有和代码一样的生命周期。

Knowledge Lifecycle
01
发现从依赖图、代码异常结构与演进历史中定位隐藏知识。
02
验证建立代码、Commit、MR、事故与人工回答组成的证据链。
03
沉淀生成结构化知识单元，记录范围、版本、证据和可信度。
04
注入在 Agent 或开发者修改代码前返回约束、风险和上下文。
05
演进代码变化后判断知识影响，按风险自动更新或人工审核。
Why It Exists

为什么需要这套系统

软件系统真正重要的知识，通常不是“这段代码做了什么”，而是“为什么必须这样做、哪些东西不能破坏、当初发生过什么”。

01

隐藏知识无法被传统知识库发现

传统知识库只能管理已经被写出来的内容，但大量业务约束、架构妥协、历史兼容逻辑和事故经验只存在于代码与开发者脑中。

02

知识会和代码逐渐分离

文档不会自动知道代码变了。随着版本演进，知识描述和真实实现出现偏差，最终让开发者基于错误上下文做决策。

03

开发者不知道自己缺少什么

开发者修改陌生模块时，往往不知道该搜索哪个关键词，也不知道这个模块曾经出现过哪些事故与特殊约束。

04

AI 编码只看当前代码仍然不够

Agent 可以理解代码结构，却无法天然知道某个“难看实现”是历史包袱、外部协议约束，还是一次线上事故后的保护逻辑。

Knowledge CI 要解决的不是“文档少”，而是“软件知识无法持续被发现、验证、使用和演进”。
System Overview

系统目标与总体闭环

像代码 CI 一样，知识也需要被检测、评估、审核、版本化和持续维护。

DISCOVERY 隐藏知识洞察 从高频修改、高依赖度模块和异常代码结构中发现潜在知识。
FRESHNESS 知识新鲜度判断 用时间、AST Diff 和 LLM 判断知识是否仍然与代码一致。
INJECTION 开发前知识注入 根据修改路径和需求，在编码行为发生前主动注入知识与风险。
EVOLUTION 增量知识演进 在 MR、Push、发布和事故修复后，增量更新相关知识。
事实层 源码、AST、依赖图、Git Diff、Commit、MR、Issue、事故记录、测试与运行时信息。
推理层 模块价值评估、异常结构识别、证据聚合、知识影响判断、风险分级与追问生成。
知识层 结构化知识单元、版本、适用范围、关联代码、证据链、置信度、负责人和审核状态。
交互层 平台审核、MCP、IDE/Agent 注入、MR Bot、知识变更通知和人工确认。
01 · Hidden Knowledge Discovery

隐藏知识洞察

目标不是检测 Code Smell 本身，而是把“长期存在、影响广泛、反复修改的异常结构”视为潜在设计知识入口。

第一步：全仓依赖分析

对整个仓库执行 AST 分析，构建文件、类、函数、模块之间的依赖图，并结合 Git 历史计算模块价值。

  • 调用依赖、继承关系、数据流和导入关系
  • 模块入度、出度、中心性和跨层依赖
  • 修改频率、回滚次数、冲突次数、贡献者数量
  • 事故修复、热点路径和历史高风险区域

Top-K 模块价值评分

不对全仓进行同等强度的昂贵分析，而是先选出最可能承载关键知识的模块。

ModuleScore = α × ChangeFrequency + β × DependencyCentrality + γ × IncidentHistory + δ × RollbackCount + ε × ContributorEntropy + ζ × CrossLayerImpact

代码结构信号

  • 魔法数字与硬编码阈值
  • 全局单例与特殊生命周期
  • 循环依赖与跨层调用
  • 桥接模块与兼容层
  • 超长函数与超长类

行为异常信号

  • 长期绕过抽象层
  • 重复但不能合并的分支
  • 异常吞噬与特殊降级
  • 特殊缓存和状态同步
  • 看似冗余却反复保留的逻辑

历史证据信号

  • 同一区域频繁修复
  • 重构后又被恢复
  • 多次回滚
  • MR 中存在长讨论
  • 事故后新增保护逻辑
Evidence Chain

从“异常代码”到“可信知识”

1

发现候选知识点

系统发现某个高依赖模块中存在全局单例、特殊锁顺序或长期保留的兼容分支。

2

回溯 Git 演进

分析该结构的引入 Commit、后续修改、回滚、MR 讨论、Issue 和事故记录。

3

评估证据充分度

区分“代码看起来特殊”与“代码和历史共同证明存在设计约束”。

4

证据不足则生成追问

把问题分配给最可能知情的负责人，等待人工补充，再生成正式知识单元。

典型追问

  • 为什么这里必须使用全局单例？
  • 这个数值来自业务规则、协议还是经验阈值？
  • 该桥接层是否用于兼容历史版本？
  • 为什么重构时仍然保留这段分支？
  • 删除它会影响哪些历史场景？
  • 这里是否发生过线上事故或数据错误？

知识单元生成原则

  • 不把模型猜测直接写成事实
  • 明确区分事实、推断和人工结论
  • 保存知识产生时对应的代码版本
  • 每条结论必须能回溯证据
  • 记录适用范围和失效条件
  • 允许后续版本化与审核
Knowledge Unit

知识单元的数据结构

知识必须是结构化、可追踪、可版本化、可判断新鲜度的，而不是一段失去上下文的自然语言摘要。

字段 作用 示例
title 知识单元标题 订单状态机禁止跨级跳转
summary 可快速注入的简明结论 PAID 不能直接进入 REFUNDED，必须经过 REFUNDING
rationale 为什么这样设计 避免支付网关异步回调导致重复退款
scope 适用模块、文件、类、函数 order-service / RefundStateMachine

owner / reviewer 负责人和审核人 支付平台组 / 架构负责人

02 · Knowledge Freshness

知识新鲜度判断

不能只看文件时间戳，也不能每次代码变化都交给大模型。需要构建一条分层、低成本、可解释的判断链路。

1时间初筛
2AST 语义过滤
3依赖影响分析
4LLM 最终判断

第一层：时间比较

如果知识最后确认时间晚于关联代码最后修改时间，通常可视为仍然新鲜；反之进入待检测队列。

第二层：AST 语义过滤

排除注释、格式化、Import 排序、无引用变量重命名、局部日志修改等无语义变更。

第三层：影响范围分析

判断修改是否触及知识关联的符号、控制流、调用关系、状态机、依赖边或对外行为。

第四层：LLM 判断

结合原知识、原证据、AST Diff、Git Diff 和 MR 描述，判断知识有效、部分失效、完全失效或产生新知识。

变更类型 是否进入 LLM 原因
注释与格式化 否 不影响语义
未引用变量重命名 通常否 无行为影响
函数签名变化 是 可能影响调用方与知识适用范围
控制流变化 是 可能改变业务规则
依赖图变化 是 可能扩大或缩小影响范围
异常处理变化 是 可能破坏历史保护逻辑
时间比较 ↓ AST Diff：是否存在语义变化？ ├─ 否 → 保持知识有效 └─ 是 ↓ 依赖分析：是否触及知识范围？ ├─ 否 → 更新验证时间 └─ 是 ↓ LLM 影响判断 ├─ 仍然有效 ├─ 局部更新 ├─ 完全失效 ├─ 产生新知识 └─ 证据不足 → 人工确认
03 · Knowledge Injection

开发前知识注入

知识不能只在平台里等待搜索，而应在开发行为发生之前，主动进入 Agent 和开发者的决策上下文。

输入信号

  • 用户自然语言需求
  • 即将读取或修改的文件路径
  • 计划调用的工具与操作
  • 相关模块依赖图
  • 历史知识单元和风险标签
  • 关联需求、Issue、测试与事故

注入内容

  • 模块设计背景与核心职责
  • 不可破坏的业务规则
  • 历史事故与踩坑记录
  • 上下游影响范围
  • 高风险依赖模块
  • 建议补充或重点运行的测试
1

Agent 准备操作

例如准备修改 order-service/refund/state_machine.ts。

2

PreToolUse / MCP 拦截

平台识别本次操作路径、用户需求和可能受影响模块。

3

检索并压缩上下文

返回最相关的知识、风险、历史事故和验证建议，而不是把整个知识库塞给 Agent。

4

继续执行修改

Agent 在理解历史原因和约束后再生成代码或执行工具。

knowledge_ci.get_context({ intent: "调整退款状态机，允许手工退款", paths: [ "order-service/refund/state_machine.ts", "order-service/payment/callback_handler.ts" ], operation: "edit" }) 返回： - 退款状态必须经过 REFUNDING - 支付网关回调可能重复，必须保持幂等 - 修改会影响账务核对与补偿任务 - 高风险模块：payment-callback / reconciliation - 建议测试：重复回调、延迟回调、部分退款、人工退款并发
04 · Incremental Evolution

知识增量演进

知识不应定期全量重建，而应在代码生命周期关键节点被增量检查、更新和审核。

触发节点

  • Git Push
  • MR 创建与更新
  • MR 合并
  • 发布前检查
  • 事故修复后
  • 架构变更后

分析内容

  • 修改了哪些模块
  • 影响哪些依赖与知识
  • 是否改变业务规则
  • 是否产生新设计决策
  • 是否让原知识过期
  • 是否需要新的风险提示

输出结果

  • 保持知识有效
  • 自动更新知识
  • 生成知识变更建议
  • 创建人工审核任务
  • 生成新的追问
  • 标记知识失效

低风险：自动融入

措辞补充、路径变化、明确证据支持的小范围更新，可自动合并并保留审计记录。

中风险：人工确认

模块职责变化、影响范围扩展、部分结论失效，需要相关负责人确认。

高风险：强制审核

推翻架构结论、修改核心规则、删除风险警告、证据冲突或跨模块重大影响，必须审核。

Agent Collaboration

Agent 与 A2A 协作设计

复杂流程不应由一个 Agent 同时完成发现、生成、评估和审核，而应拆成职责明确的协作单元。

ANALYSIS AGENT

代码分析 Agent

负责 AST、依赖图、热点模块、异常结构和语义 Diff 分析。

EVIDENCE AGENT

证据聚合 Agent

负责检索 Commit、MR、Issue、事故记录和历史讨论，构建证据链。

KNOWLEDGE AGENT

知识生成 Agent

根据证据生成知识草稿、适用范围、失效条件和追问。

RISK AGENT

风险评估 Agent

判断知识变更的影响范围、证据冲突和自动融入风险。

REVIEW AGENT

审核辅助 Agent

为人工审核生成差异摘要、证据说明和推荐处理意见。

INJECTION AGENT

知识注入 Agent

根据当前需求和修改路径选择最相关、最小充分的上下文。

Reference Architecture

参考系统架构

从代码采集、静态分析、证据聚合到知识服务与开发流程集成，形成可持续运行的平台能力。

接入层 GitHub / GitLab / Gitea、Webhooks、MR Bot、IDE 插件、MCP Server、Agent Hooks。
分析层 语言解析器、AST 服务、依赖图服务、Git Diff 服务、热点模块分析、语义变更检测。
证据层 Commit、MR、Issue、评论、事故记录、测试结果、运行日志、人工回答与负责人映射。
智能层 知识候选生成、证据充分度评估、追问生成、知识影响判断、风险分级和上下文压缩。
存储层 关系数据库、对象存储、图数据库、向量索引、版本与审核记录、知识状态机。
应用层 知识平台、审核工作台、模块风险视图、知识图谱、MCP、MR 评论与通知系统。

推荐存储划分

  • PostgreSQL：知识单元、版本、审核、追问、负责人
  • Graph DB：模块、符号、依赖和影响关系
  • Object Storage：AST 快照、Diff、证据原文
  • Vector Index：知识、Commit、MR 与问题语义检索
  • Cache：热点知识与开发前注入结果

关键工程要求

  • 所有结论可追溯到证据
  • 所有自动更新可回滚
  • 支持多语言仓库与增量解析
  • 模型调用必须分层控成本
  • 人机交互必须进入状态机
  • 注入上下文需要最小充分原则
Observability

可观测性与核心指标

Knowledge CI 不是一个“生成了多少文档”的系统，而应衡量知识是否被发现、验证、使用和持续保持有效。

覆盖率高价值模块中已有有效知识的比例
新鲜度知识与当前代码版本保持一致的比例
命中率开发前注入知识被实际采用的比例
确认率AI 候选知识被人工确认的比例

发现质量

  • 候选知识精确率
  • 有效追问率
  • 人工补充率
  • 高价值模块覆盖率

演进质量

  • 过期知识发现时延
  • 误报率与漏报率
  • 自动更新回滚率
  • 审核平均处理时长

使用价值

  • MCP 注入命中率
  • 风险提示采纳率
  • 重复事故下降比例
  • 陌生模块理解时间下降比例
Implementation Roadmap

分阶段落地路线

先建立可信的分析与知识闭环，再扩展到主动注入和多 Agent 协作，避免一开始就做成庞大而不可控的平台。

PHASE 1

知识发现 MVP

  • 单语言 AST 分析
  • 依赖图与 Top-K 模块
  • Git Log 证据聚合
  • 候选知识与追问
  • 基础审核平台
PHASE 2

新鲜度与增量演进

  • 知识—代码关联
  • AST Diff 语义过滤
  • MR / Push 触发
  • 风险分级
  • 知识版本与回滚
PHASE 3

开发前注入与平台化

  • MCP Server
  • Agent Hook 集成
  • 上下文压缩
  • A2A Agent 协作
  • 多仓库知识治理
最适合优先验证的 MVP 场景

选择一个历史较长、改动频繁、事故记录较多、核心开发者仍在团队中的仓库。先验证系统能否发现 10～30 条真正有价值的隐藏知识，而不是追求全仓覆盖。

第一阶段不应该做什么
  • 不要一开始支持所有语言和所有代码结构
  • 不要直接自动写入正式知识库
  • 不要把普通代码摘要当作知识
  • 不要完全依赖向量检索代替符号与依赖分析
  • 不要把所有代码变化都交给 LLM
最核心的产品壁垒

不是某个单独的 AST 规则，也不是一个更好的代码问答模型，而是知识发现、证据验证、人机追问、开发前注入、增量演进与风险治理组成的完整闭环。

Knowledge CI 不是普通 Wiki，不是单纯代码 RAG，也不是自动生成文档的工具。 它管理的是：代码为什么这样设计、这些结论现在是否仍然成立、修改时必须知道什么，以及代码变化后知识如何继续演进。
